# 一手销售数据业务流程说明文档

> 版本：V1.0  
> 日期：2026年7月23日  
> 状态：初稿  
> 关联文档：PRD V1.4、DDL V1.4  

---

## 1. 文档概述

本文档基于《AI赋能香港房地产——智能问数与报告系统（PRD V1.4）》及对应的数据库设计（DDL），详细描述一手住宅销售数据的**自动处理流程**和**人工介入处理流程**。旨在为开发、运维、数据治理人员提供清晰的业务操作指引，确保数据从采集、解析、入库到人工修正的全链路规范运行。

---

## 2. 数据模型总览

系统采用**五层数据模型**，所有业务流程均围绕以下层级展开：

| 层级 | 表名 | 说明 |
| :---: | :--- | :--- |
| L1 | `ai_sales_projects` | 楼盘主数据（含总可售单元数） |
| L2 | `ai_sales_unit_types` | 户型分类（人工精修核心） |
| L2 | `ai_sales_salesbrochures` | 销售安排/说明书 |
| L3 | `ai_sales_price_lists` | 价单头信息 |
| L3 | `ai_sales_price_list_items` | 价单明细项 |
| L4 | `ai_sales_units` | 物理单元（具体到座/楼层/单位号） |
| L5 | `ai_sales_transactions` | 销售/成交记录 |

**关联关系**：
- 楼盘（L1）下包含多个户型分类、多份销售安排、多个物理单元
- 销售安排（L2）下可关联多份价单（L3）
- 价单明细项（L3）通过 `block+floor_no+unit_no` 匹配到物理单元（L4）
- 物理单元（L4）通过 `is_sold` 状态及 `latest_transaction_id` 关联最新交易记录（L5）
- 户型分类（L2）通过 `unit_type_id` 绑定物理单元，用于聚合分析（如M015户型热度排名）

## 3. 一手销售数据自动处理流程

自动处理流程由**爬虫系统**和**解析引擎**协作完成，目标是将外部数据源（一手住宅物业销售资讯网等）中的结构化/半结构化数据自动提取、转换并加载至MySQL数据库。

### 3.1 整体流程（泳道式描述）

```mermaid
flowchart TD
    A[定时调度触发] --> B[爬虫抓取外部数据文件]
    B --> C{数据文件类型}
    C -->|楼盘说明书| D[解析楼盘说明书]
    C -->|销售安排| E[解析销售安排]
    C -->|价单| F[解析价单]
    C -->|成交记录| G[解析成交记录]
    
    D --> D1[提取楼盘静态信息]
    D --> D2[提取户型描述]
    D --> D3[提取物理单元文字描述]
    D3 --> D4[将文字描述转换为具体单元记录]
    
    E --> E1[提取销售安排信息<br>（推出日期/单位总数等）]
    E --> E2[提取物理单元清单<br>（座/楼层/单位号）]
    
    F --> F1[提取价单头信息<br>（编号/日期/版本）]
    F --> F2[提取价单明细项<br>（座/楼层/单位号/面积/价格）]
    
    G --> G1[提取交易记录<br>（日期/价格/面积/原始户型文本）]
    
    D1 --> H[写入/更新 L1 ai_sales_projects]
    D2 --> I[写入/更新 L2 ai_sales_unit_types]
    D4 --> J[写入/更新 L4 ai_sales_units]
    E1 --> K[写入/更新 L2 ai_sales_salesbrochures]
    E2 --> J
    F1 --> L[写入/更新 L3 ai_sales_price_lists]
    F2 --> M[写入/更新 L3 ai_sales_price_list_items]
    G1 --> N[写入/更新 L5 ai_sales_transactions]
    
    J --> O[自动匹配物理单元与户型类型<br>（基于unit_type_id或规则）]
    M --> P[自动匹配价单项与物理单元<br>（基于block+floor+unit_no）]
    N --> Q[自动关联交易记录与物理单元<br>（基于匹配规则）]
    
    Q --> R[更新物理单元销售状态 is_sold]
    R --> S[结束（记录日志）]
```

### 3.2 各步骤详细说明

#### 3.2.1 爬虫抓取
- **触发方式**：按天定时（如每日凌晨2:00）或手动触发。
- **抓取内容**：
  - 楼盘主列表（含详情页URL）
  - 楼盘说明书（PDF/HTML）
  - 销售安排文件（PDF/HTML）
  - 价单文件（PDF/HTML）
  - 成交记录列表（HTML表格/JSON）
- **防重机制**：通过 `(data_source_id, external_id)` 唯一键避免重复入库。

#### 3.2.2 楼盘说明书解析
- **输入**：楼盘详情页或PDF说明书。
- **输出**：
  - **楼盘静态信息**：楼盘中文名、期数、区域、地址、总可售单元数、座数等 → 写入 `ai_sales_projects`。
  - **户型描述**：从说明书中提取户型名称、卧室/厅/卫数量、是否开放式厨房、阳台/露台信息等 → 写入 `ai_sales_unit_types`（初始 `is_manual_modified=0`）。
  - **物理单元文字描述**：例如“第1A座2楼A室”等文本 → 需**进一步转换**为结构化记录。

#### 3.2.3 物理单元文字描述 → 结构化记录
- **规则引擎**：采用正则表达式或NLP模型将自然语言描述拆解为 `block`（座）、`floor_no`（楼层）、`unit_no`（单位号）。
- 示例：`"第1A座15楼A室"` → `block='第1A座'`, `floor_no='15'`, `unit_no='A室'`。
- **去重**：同一楼盘下 `(block, floor_no, unit_no)` 唯一，如有重复则更新。
- 写入 `ai_sales_units`，同时尝试匹配已存在的户型类型（通过户型名称或面积区间）。

#### 3.2.4 销售安排解析
- **输入**：销售安排PDF/HTML。
- **输出**：
  - 头信息：推出日期、单位总数、楼层范围摘要等 → 写入 `ai_sales_salesbrochures`。
  - **物理单元清单**：若销售安排中包含具体的单位列表（座/楼层/单位号），则解析后写入 `ai_sales_units`（若尚不存在），并自动关联 `brochure_id`。

#### 3.2.5 价单解析
- **输入**：价单PDF（通常包含表格式单位价格）。
- **输出**：
  - 头信息：价单编号、印发日期、修订版本 → 写入 `ai_sales_price_lists`。
  - 明细项：每个单位的座/楼层/单位号、实用面积（平方米/平方呎）、露台面积、售价、是否连车位等 → 写入 `ai_sales_price_list_items`。
  - **自动匹配物理单元**：根据 `(project_id, block, floor_no, unit_no)` 在 `ai_sales_units` 中查找对应 `unit_id`，匹配成功则填充 `price_list_items.unit_id`，失败则留空待人工处理。

#### 3.2.6 成交记录解析
- **输入**：成交列表HTML/API。
- **输出**：
  - 交易记录：成交日期、成交价、实用面积、原始户型文本、楼层、单位号等 → 写入 `ai_sales_transactions`。
  - **自动匹配物理单元**：同样依据 `(project_id, block, floor_no, unit_no)` 尝试匹配 `unit_id`，匹配成功则关联，同时更新物理单元的 `is_sold=1`、`sold_date` 和 `latest_transaction_id`。
  - **匹配失败**：记录 `unit_id=NULL`，待人工处理。

#### 3.2.7 关联同步（自动后处理）
- **户型绑定**：若物理单元已存在 `unit_type_id` 则跳过；否则尝试通过 `unit_type_raw` 或面积区间匹配 `ai_sales_unit_types`。
- **价单与销售安排关联**：若价单的 `brochure_id` 为空，系统可依据日期（价单印发日期与销售安排推出日期相近）或人工规则进行自动推荐（但首期建议人工确认）。
- **去化率相关**：物理单元 `is_sold` 状态更新后，系统自动计算楼盘已售数量（通过聚合 `ai_sales_units` 中 `is_sold=1` 的记录），但去化率（M012）在查询时实时计算，不单独存储。

### 3.3 自动处理异常处理
| 异常场景 | 处理策略 |
| :--- | :--- |
| 解析失败（PDF格式不兼容） | 记录错误日志，标记该文件为“待人工处理”，后台提供手动上传/修正入口 |
| 物理单元匹配冲突（重复） | 根据 `uk_project_block_floor_unit` 唯一键，新数据覆盖旧数据（保留最新） |
| 价单项无法匹配物理单元 | 保留 `unit_id=NULL`，在后台“价单管理”中高亮提示，供管理员手动匹配 |
| 交易记录无法匹配物理单元 | 同样保留 `unit_id=NULL`，在后台“销售记录管理”中高亮提示 |

## 4. 一手销售数据人工介入处理流程

人工介入主要在**管理后台**进行，针对自动处理中未能准确提取、匹配或需要修正的数据进行维护。**核心原则**：人工修改直接覆盖数据库原始值，标记 `is_manual_modified=1`，记录修改人和时间，不采用权重体系。

### 4.1 楼盘静态信息维护

- **入口**：后台“楼盘管理”。
- **允许操作**：
  - 编辑楼盘基本信息（名称、区域、地址、总可售单元数等）。
  - 修改后自动设置 `is_manual_modified=1`，记录 `modified_by_user_id` 和 `modified_at`。
- **同步影响**：楼盘信息变更可能影响去化率计算（`total_units`）及区域聚合，需刷新相关缓存。

### 4.2 户型信息更新与同步

- **入口**：后台“户型类型管理”（核心精修模块）。
- **操作场景**：
  1. **新增户型**：为某楼盘创建新的户型类型，填写标准化名称和结构化属性（卧室/厅/卫、是否开放式厨房等）。
  2. **编辑户型**：修改已有户型属性，修改后标记人工修改。
  3. **关联售楼说明书**：在编辑页面可查看该楼盘的所有销售安排PDF，管理员可直接打开对照，辅助判断户型属性。
  4. **批量绑定物理单元**：选择一批物理单元（可按座/楼层范围筛选），一键绑定到某个户型类型。此操作将更新 `ai_sales_units.unit_type_id`。
- **同步更新要求**：
  - 当户型类型被修改（如卧室数量变更），已绑定该户型的物理单元**不会自动更新**属性（物理单元只存储 `unit_type_id`，户型属性集中管理）。但**户型热度排名（M015）** 等指标会基于新的 `unit_type_id` 重新聚合，因此历史交易记录无需调整。
  - 若管理员删除某个户型类型，系统需检查是否仍有物理单元引用，若有则禁止删除或提示先解绑。

### 4.3 物理单元管理（增删改及触发重新提取）

- **入口**：后台“物理单元管理”。
- **允许操作**：
  - **新增**：手动添加一个物理单元（填写座/楼层/单位号、面积、朝向等）。
  - **编辑**：修改单元属性（面积、朝向、户型类型、销售状态等）。
  - **删除**：逻辑归档（`is_archived=1`），物理删除仅限未关联任何交易/价单的单元。
  - **批量操作**：批量修改户型类型或销售安排。
- **触发重新提取**：
  - 管理员在修改某个楼盘的部分单元后，可**手动触发**重新提取该楼盘的所有销售安排、价单、成交记录数据（即重新执行解析流程），以刷新关联关系。
  - **注意**：触发重新提取**不会覆盖人工修改过的字段**（`is_manual_modified=1` 的字段值保持不变），仅更新未人工修改的部分。
- **同步更新要求**：
  - 物理单元 `unit_type_id` 变更后，需同步更新该单元关联的交易记录中可能缓存的户型信息（但交易记录本身只存 `unit_id`，因此无需更新，指标查询时通过 `unit_id` 关联获取最新户型）。
  - 物理单元删除/归档时，关联的价单项（`ai_sales_price_list_items.unit_id`）置为 `NULL`，交易记录（`ai_sales_transactions.unit_id`）置为 `NULL`。

### 4.4 销售安排、价单、成交记录的增删改与重新提取

- **入口**：后台分别对应的管理页面（销售安排管理、价单管理、销售记录管理）。
- **允许操作**：
  - **新增**：手动上传文件或录入数据，系统解析后入库。
  - **编辑**：修改头信息或明细项，修改后标记人工修改。
  - **删除**：逻辑归档（`is_archived=1`）。
  - **合并**：重复记录合并（设置 `merged_into_id`）。
- **触发单独重新提取**：
  - 对某个销售安排、价单或成交记录文件，管理员可点击“重新解析”按钮，系统重新执行该文件的提取逻辑，**覆盖**已有数据（但保留人工修改过的字段不覆盖）。
- **匹配物理单元（人工）**：
  - 对于自动匹配失败的价单项或交易记录，后台提供**手动匹配**界面，管理员可浏览物理单元列表并选择正确的 `unit_id` 进行绑定。
  - 支持批量匹配（按座/楼层/单位号规则匹配）。
- **同步更新要求**：
  - 价单新增/修改后，若影响 `price_list_items.unit_id` 或价格信息，需重新计算相关指标（如M017价单均价、M018折让率），并在查询时反映最新数据。
  - 交易记录新增/修改后，需更新对应物理单元的 `is_sold`、`sold_date`、`latest_transaction_id`。若交易记录被删除或归档，需重新计算该物理单元的最新销售状态。

## 5. 数据一致性保障

### 5.1 人工修改覆盖规则
- 任何表只要有 `is_manual_modified` 字段，系统在**自动流程**（爬虫/解析）更新时，**必须**检查该字段：
  - 若 `is_manual_modified=0`，允许覆盖。
  - 若 `is_manual_modified=1`，**跳过**该字段的自动更新，仅更新其他未人工修改的字段（如 `updated_at`）。
- 人工修改操作（后台编辑）直接写入新值，并设置 `is_manual_modified=1`。

### 5.2 级联同步规则
| 父表变更 | 子表影响 | 处理方式 |
| :--- | :--- | :--- |
| 楼盘被归档/删除 | 其下所有户型、物理单元、价单、销售安排、交易记录 | 不允许物理删除（外键约束），仅逻辑归档或级联软删除 |
| 户型类型删除 | 绑定的物理单元 `unit_type_id` 置为NULL | 在删除前由管理员确认，系统自动置NULL |
| 物理单元删除/归档 | 价单项、交易记录 `unit_id` 置为NULL | 外键 `ON DELETE SET NULL` |
| 销售安排删除 | 关联价单 `brochure_id` 置为NULL | 外键 `ON DELETE SET NULL` |
| 价单删除 | 明细项级联删除（`ON DELETE CASCADE`） | 自动处理 |
| 价单项 `unit_id` 变更 | 关联物理单元的价格信息（如用于计算折让率） | 实时查询时反映，无需存储冗余 |

### 5.3 审计与追溯
- 所有人工修改操作均记录 `modified_by_user_id` 和 `modified_at`，可在后台“审计日志”中查看修改历史（可选功能）。
- 数据溯源信息（`data_source_id`, `external_id`, `source_url`）在所有核心表中保留，确保每个数据点可追溯至原始来源。

## 8. 附录：常见问题与注意事项

| 问题 | 处理建议 |
| :--- | :--- |
| 自动解析中价单面积单位混乱（平方米/平方呎） | 系统应统一存储为平方呎（如需），解析时通过 `saleable_area_sqm` 和 `saleable_area_sqft` 分别存储，保留原始值 |
| 物理单元匹配率低（<80%） | 检查爬虫是否完整抓取物理单元清单；可通过后台批量匹配功能人工补全 |
| 人工修改后重新解析是否会丢失修改？ | 不会，系统检查 `is_manual_modified` 标记，跳过人工修改字段 |
| 去化率计算依赖 `total_units`，若该字段缺失 | 系统中 M012 不予计算，并在报告中注明“该楼盘无总可售数据，无法计算去化率” |
| 跨表关联时外键约束导致删除失败 | 应先归档关联子表或解除绑定，再进行父表操作 |
