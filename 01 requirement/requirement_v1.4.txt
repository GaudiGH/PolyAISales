**版本**：V1.4
**日期**：2026年7月22日
**状态**：定稿
**更新说明**：
- 去除三层权重体系（raw/auto_cleaned/human_verified），人工修改直接覆盖并标记
- 新增物理单元层级（ai_sales_units），建立五层数据模型

## 一、项目概述

### 1.1 项目背景

香港房地产投资与销售领域缺乏系统化的AI深度应用，数据分散于多个平台、格式各异，整理高度依赖人工收集与Excel加工，数据获取滞后，决策支持不足。AI Agent与RAG技术已在国内市场逐步成熟，香港市场仍存在明显空白。本项目旨在通过AI技术建立一套可持续扩展的智能数据分析底座，协助团队更快掌握一二手楼盘动态，将分散的市场信息转化为可行的销售洞察。

### 1.2 项目定位

- **混合型项目**：内部投资分析团队先行使用，架构设计同时具备对外服务扩展能力
- **核心交付**：自然语言问数 + 自动化报告生成
- **数据聚焦**：首期覆盖一手住宅市场（含价单数据），架构预留二手数据扩展能力
- **交互渠道**：Web端为主（完整功能），微信服务号为辅（轻量问数）
- **多语言**：框架层支持中英文双语，首期以中文为主

### 1.3 项目目标（优先级排序）

| 优先级 | 维度 | 目标描述 |
| :---: | :--- | :--- |
| 1 | 用户满意度 | 简洁、快速、可信的对话式数据查询体验 |
| 2 | 数据准确度 | 每个数据点可溯源、可复核，禁止AI捏造 |
| 3 | 数据覆盖度 | 首期覆盖一手住宅物业销售资讯网全量数据（含价单） |
| 4 | 系统稳定性 | 稳定运行，可用率≥99.5% |
| 5 | 商业变现 | 首期不涉及，为后续商业化预留架构空间 |

## 四、数据源与数据治理

### 4.1 数据源定义

| 数据源 | 类型 | 首期 | 扩展预留 |
| :--- | :--- | :---: | :---: |
| 一手住宅物业销售资讯网 | 一手楼官方数据（含价单） | ✅ | — |
| 某二手网站（具体待定） | 二手楼公开数据 | ❌ | ✅ 架构预留 |

### 4.2 数据更新

- **频率**：按天更新
- **时间范围**：按数据源网站实际发布的数据为准
- **地理覆盖**：全港18区

### 4.3 数据治理模型

**核心原则：人工修改直接覆盖，仅标记来源，不使用权重体系**

| 数据状态 | 说明 | 标记方式 |
| :--- | :--- | :--- |
| 爬虫原始采集 | 首次入库的数据，未经人工处理 | `is_manual_modified = 0` |
| 人工修改 | 管理员在后台直接修改后覆盖原值 | `is_manual_modified = 1`，记录 `modified_by_user_id` 和 `modified_at` |

**查询取数逻辑（简化）**：
- 直接查询最新数据，不考虑权重层级
- 查询结果中可筛选/展示“已人工确认”的数据（`is_manual_modified = 1`）
- 所有数据平等参与指标计算，人工修改仅作为数据来源标记

**人工精修定位**：
- 管理员在后台完成数据修正，**直接覆盖**原数据库记录
- 修改操作记录修改人和修改时间，便于追溯
- 审计日志作为可选功能，记录修改前后值

### 4.4 数据回溯与修正

| 功能 | 说明 |
| :--- | :--- |
| 数据修改 | 管理员可修改价格、面积、区域、地址、户型类型等任意字段，修改后 `is_manual_modified = 1` |
| 记录合并 | 合并重复记录，保留最优字段组合，被合并记录标记 `merged_into_id` |
| 记录存档 | 标记 `is_archived = 1`，查询时默认过滤 |
| 审计日志 | 可选记录（功能存在，不强制填写修改理由） |


## 五、数据模型（核心）

### 5.1 数据模型层级

系统采用**五层数据模型**：

```
楼盘（ai_sales_projects）
  ├── 户型分类（ai_sales_unit_types）  ← 人工精修核心
  ├── 销售安排/说明书（ai_sales_salesbrochures）
  │     └── 价单（ai_sales_price_lists）
  │           └── 价单项（ai_sales_price_list_items）
  └── 物理单元（ai_sales_units）
        └── 销售记录（ai_sales_transactions）
```

### 5.2 各层级说明

| 层级 | 表名 | 说明 |
| :---: | :--- | :--- |
| L1 | `ai_sales_projects` | 楼盘主数据，包含总可售单元数（用于去化率计算） |
| L2 | `ai_sales_unit_types` | **人工精修核心**——户型分类，包含卧室/厅/卫数量、是否开放式厨房、阳台数量、露台面积、是否复式等属性 |
| L2 | `ai_sales_salesbrochures` | 销售安排/说明书，记录开发商分阶段推售的文件信息（PDF链接、推出单位总数、状态等） |
| L3 | `ai_sales_price_lists` | 价单头信息，关联销售安排，记录价单编号、印发日期、版本、修订日期等 |
| L3 | `ai_sales_price_list_items` | 价单明细项，记录每个物理单元在价单中的售价、实用面积、露台面积等 |
| L4 | `ai_sales_units` | 物理单元（具体到座/楼层/单位号），关联户型分类和销售安排 |
| L5 | `ai_sales_transactions` | 销售/成交记录，关联到物理单元 |

### 5.3 价单与物理单元的关系

| 关系 | 说明 |
| :--- | :--- |
| **价单项 → 物理单元** | 价单项通过 `unit_id` 关联物理单元，提供该单元在特定价单中的**定价参考** |
| **价单项 → 物理单元匹配** | 通过 `project_id` + `block` + `floor_no` + `unit_no` 自动匹配；匹配失败时人工处理 |
| **面积数据传递** | 价单中的 `saleable_area` 可自动填充物理单元缺失的面积信息（不覆盖人工修正值） |
| **版本关联** | 同一物理单元在不同价单版本中可能有不同定价，支持价格变化追溯 |
| **定价-成交对比** | 通过 `unit_id` 关联价单定价与实际成交记录，计算折让率 |

### 5.4 核心表清单

| 序号 | 表名 | 说明 |
| :---: | :--- | :--- |
| 1 | `ai_sales_data_sources` | 数据源配置表 |
| 2 | `ai_sales_regions` | 香港行政区划表（18区，中英文预留） |
| 3 | `ai_sales_projects` | 楼盘主数据表（含总可售单元数） |
| 4 | `ai_sales_salesbrochures` | 销售安排/说明书表（分阶段推售） |

| 6 | `ai_sales_price_list_items` | 价单明细项表（新增） |

## 六、核心业务指标定义（预定义指标层）

**关键原则**：以下指标在系统中**预先定义、硬编码计算逻辑**。AI仅做“问题→指标映射”，不做“指标定义”或“口径解释”。所有指标的计算基于MySQL数据库中的结构化数据，通过确定性SQL执行。

### 6.1 基础统计指标

| 指标ID | 指标名称 | 业务定义 | SQL计算逻辑 | 单位 |
| :---: | :--- | :--- | :--- | :--- |
| M001 | 成交量 | 符合条件的成交记录总数 | `COUNT(*)` | 宗 |
| M002 | 成交总金额 | 符合条件的成交价总和 | `SUM(price)` | 港元 |
| M003 | 成交总面积 | 符合条件的实用面积总和 | `SUM(saleable_area)` | 平方呎 |
| M004 | 平均成交价 | 成交总金额 ÷ 成交量 | `SUM(price) / COUNT(*)` | 港元 |
| M005 | 平均成交呎价 | 成交总金额 ÷ 成交总面积 | `SUM(price) / SUM(saleable_area)` | 港元/呎 |
| M006 | 最高成交呎价 | 符合条件的最高呎价 | `MAX(price / saleable_area)` | 港元/呎 |
| M007 | 最低成交呎价 | 符合条件的最低呎价 | `MIN(price / saleable_area)` | 港元/呎 |
| M008 | 中位数成交价 | 符合条件的成交价中位数 | `PERCENTILE_CONT(0.5) WITHIN GROUP(ORDER BY price)` | 港元 |

### 6.2 时间对比指标

| 指标ID | 指标名称 | 业务定义 | SQL计算逻辑 | 单位 |
| :---: | :--- | :--- | :--- | :--- |
| M009 | 环比变化率 | (本月值 - 上月值) ÷ 上月值 × 100% | 窗口函数 `LAG` 计算 | 百分比 |
| M010 | 同比变化率 | (本月值 - 去年同月值) ÷ 去年同月值 × 100% | 窗口函数 `LAG` 指定偏移12个月 | 百分比 |
| M011 | 日均成交量 | 月成交量 ÷ 当月天数 | `COUNT(*) / DAY(LAST_DAY(date))` | 宗/天 |

### 6.3 衍生指标（需多表/多层计算）

| 指标ID | 指标名称 | 业务定义 | 计算逻辑 | 单位 |
| :---: | :--- | :--- | :--- | :--- |
| M012 | **去化率** | 某楼盘已售物理单元数 ÷ 总可售单元数 × 100% | `已售物理单元数 / total_units * 100` | 百分比 |
| M013 | **区域热度（成交量占比）** | 某区域成交量占全港成交量的比重 | `某区域成交量 / 全港总成交量 * 100` | 百分比 |
| M014 | **区域热度（价格涨幅）** | 某区域本月均价环比上月均价的涨幅 | `(本月均价 - 上月均价) / 上月均价 * 100` | 百分比 |
| M015 | **户型热度排名** | 按成交记录数统计各户型分类的排名 | `GROUP BY unit_type_id ORDER BY COUNT(*) DESC` | 排名 |
| M016 | **楼盘成交集中度** | 某楼盘成交量占所在区域成交量的比重 | `某楼盘成交量 / 所在区域成交量 * 100` | 百分比 |

### 6.4 价单相关指标（V1.4新增）

| 指标ID | 指标名称 | 业务定义 | 计算逻辑 | 单位 |
| :---: | :--- | :--- | :--- | :--- |
| M017 | **价单均价** | 某项目/区域在有效价单中的平均定价 | `AVG(price_list_items.price)` | 港元/呎 |
| M018 | **价单vs成交折让率** | (成交均价 - 价单均价) ÷ 价单均价 × 100% | 价单均价与成交均价的差异率 | 百分比 |

**价单指标数据依赖说明**：
- M017 依赖 `ai_sales_price_lists`（最新有效价单）和 `ai_sales_price_list_items`（价单项）
- M018 需同时有价单数据和成交记录（`ai_sales_transactions`），两者通过 `unit_id` 关联
- 价单数据缺失时，M017和M018不予计算（不猜测、不填充）

### 6.5 去化率（M012）的特殊说明

去化率是房地产行业的**核心指标**，其计算基于物理单元表：

| 数据项 | 来源 | 说明 |
| :--- | :--- | :--- |
| 已售单元数 | `ai_sales_units.is_sold = 1` | 系统根据交易记录自动更新 `is_sold` 状态 |
| 总可售单元数 | `ai_sales_projects.total_units` | 从楼盘详情页爬取的“总单位数”字段 |

**系统实现要求**：
- 爬虫需采集每个楼盘的“总可售单元数”字段，写入 `ai_sales_projects.total_units`
- 若某楼盘 `total_units` 为 `NULL`，去化率指标对该楼盘**不予计算**（不猜测、不填充）
- 报告中涉及去化率时，需注明：“去化率基于已采集到总可售数据的X个楼盘计算”

### 6.6 指标映射规则（AI理解→指标绑定）

当用户提问中包含以下关键词时，系统自动映射至对应指标：

| 用户关键词（示例） | 映射指标 | 备注 |
| :--- | :--- | :--- |
| “均价”“平均价格”“多少钱一呎” | M005 平均成交呎价 | 默认指实用面积呎价 |
| “成交量”“卖了多少套”“成交宗数” | M001 成交量 | — |
| “卖得最好”“最火”“第一名” | M015 户型热度排名 或 M013 区域热度 | 根据上下文判断维度 |
| “去化”“去化率”“卖掉多少比例” | M012 去化率 | 仅对有总可售数据的楼盘有效 |
| “涨了还是跌了”“环比” | M009 环比变化率 | 默认指均价环比 |
| “同比” | M010 同比变化率 | 默认指均价同比 |
| “总金额”“成交额” | M002 成交总金额 | — |
| “价单”“定价”“价单价格” | M017 价单均价 | 可进一步指定座/楼层/单位 |
| “折让”“价单折让” | M018 价单vs成交折让率 | 需同时有价单和成交数据 |

### 6.7 指标扩展机制

当用户提出**未预定义**的指标需求时，系统行为：
1. 识别为“未支持指标”
2. 主动反问：“系统暂未支持【XX】指标分析。您可以查询以下已支持的指标：[列出M001-M018列表]”
3. **严禁**AI自行定义或计算新指标口径

### 7.2 智能问数功能

**FR-01：自然语言查询**
- 用户通过Web或微信输入自然语言问题
- 系统执行意图识别：区域、时间、面积段、价格段、指标类型（均价/成交量/去化率/热度/排名/趋势/价单）
- 系统执行指标映射：将意图绑定至预定义指标（M001-M018）
- 返回结构化数据结果
- 底层数据查询基于五层模型（楼盘→户型/销售安排/价单→物理单元→交易记录）

**FR-02：返回结果格式**
- 主要数据点 + 简短解读
- 每个数据点附带引用溯源标注 `[n]`
- 溯源信息包含：**查询ID、数据来源、记录数、查询时间戳**

**FR-03：引用溯源展示**
- **Web端**：引用标记可点击，弹窗显示完整溯源详情（含查询ID、来源、记录数、时间戳）
- **微信端**：以文本脚注形式呈现 `[n]`（如“[1] 一手住宅物业销售资讯网 | 87条记录”）

**FR-04：主动澄清**
以下情况系统**必须反问**而非猜测：
- 区域名称模糊（如“港岛那边”）
- 时间范围不明（如“最近”）
- 指标名称不明确（如“卖得怎么样” → 反问“您是指成交量还是均价？”）
- 用户提到未预定义的指标
- 查询条件无匹配记录

**FR-05：低数据量提示**
- 当匹配记录 ≤ 5条时，返回结果并提示：“仅找到X条记录，结果仅供参考”

**FR-06：Web端图表渲染**
- 趋势查询返回趋势图（折线图）
- 排名查询返回排名图（柱状图/横向柱状图）
- 对比查询返回对比图（分组柱状图）

## 九、后台管理功能（V1.4 重构）

### 9.1 核心管理模块

后台管理以**户型类型管理**和**价单管理**为核心。

#### 9.1.1 户型类型管理（核心精修模块）

**功能定位**：这是后台管理的**核心功能**，所有数据精修工作围绕户型类型展开。

| 功能 | 说明 |
| :--- | :--- |
| **列表浏览** | 按项目/销售安排筛选，展示所有户型类型记录，高亮 `is_manual_modified=1` 的记录 |
| **新增户型** | 为某楼盘创建新的户型类型，填写 `unit_name`、卧室/厅/卫数量、是否开放式厨房、阳台数量、露台面积、是否复式等 |
| **编辑户型** | 修改户型名称或属性，修改后自动设置 `is_manual_modified=1`、记录修改人和时间 |
| **关联售楼说明书** | 编辑页面可查看该楼盘关联的 `ai_sales_salesbrochures` 列表，管理员可**打开PDF对照**户型信息，辅助判断 |
| **关联价单对照** | 可查看该楼盘的最新价单明细，通过价单中的单位分布/户型描述辅助判断户型类型 |
| **批量绑定** | 将一批物理单元批量绑定到某个户型类型（如“A座2-27楼A室”全部绑定到“2房2厅”） |
| **删除/归档** | 归档不再使用的户型类型 |

**户型精修操作流程**：

```
1. 管理员进入户型类型管理 → 按楼盘筛选
2. 查看该楼盘关联的销售安排列表 → 点击PDF链接打开售楼说明书
3. 查看该楼盘关联的最新价单 → 对照单位分布
4. 对照PDF中的户型描述 → 判断该楼盘包含哪些户型
5. 新增/编辑户型类型 → 填写标准化名称和结构化属性
6. 进入物理单元管理 → 将对应物理单元批量绑定到该户型类型
7. 绑定后，该楼盘下的交易记录可按户型类型进行聚合统计
```

#### 9.1.2 价单管理（V1.4新增）

**功能定位**：管理开发商发布的价单（Price List），支持价单导入、版本管理、物理单元匹配和价格对比分析。

| 功能 | 说明 |
| :--- | :--- |
| **价单列表** | 按项目/销售安排筛选，显示所有价单版本，高亮最新版本。列表展示：价单编号、印发日期、总单位数、状态（草稿/已发布/已取代） |
| **上传/导入价单** | 管理员上传价单PDF，系统自动解析并生成价单头信息及明细项。解析内容：价单编号、印发日期、各单位的座/楼层/单位号、实用面积、售价、露台面积等 |
| **编辑价单** | 修改头信息（价单编号、印发日期等）或明细项（价格、面积等），修改后自动标记 `is_manual_modified = 1` |
| **匹配物理单元** | 对价单明细项（`unit_id = NULL`），管理员手动选择对应的物理单元进行绑定。匹配依据：`project_id` + `block` + `floor_no` + `unit_no` |
| **批量匹配** | 根据座/楼层/单位号规则，批量将价单项绑定到物理单元 |
| **关联销售安排** | 将价单绑定到对应的销售安排（`brochure_id`），支持同一销售安排多版本价单管理 |
| **版本管理** | 同一价单编号可存在多个修订版本，标记 `is_latest` 区分最新版本，历史版本保留供追溯 |
| **价单 vs 成交对比** | 展示某物理单元的**价单定价**与实际**成交价**对比，支持按项目/区域/户型维度聚合分析 |

**价单管理操作流程**：

```
1. 爬虫抓取/管理员上传价单PDF
       ↓
2. 系统解析PDF → 生成价单头信息 + 明细项
       ↓
3. 管理员检查解析结果，必要时手动修正价格/面积
       ↓
4. 系统自动匹配：通过 block+floor_no+unit_no 关联物理单元
       ↓
5. 管理员确认匹配结果，手动补匹配未关联的条目
       ↓
6. 价单与销售安排关联（如属于某份销售安排）
       ↓
7. 标记为“已发布” → 数据可用于价格查询和报告
```

## 十、AI Agent行为规则（核心约束）

以下规则为硬约束，任何Agent不得违反：

| 规则编号 | 规则内容 | 触发场景 |
| :---: | :--- | :--- |
| R1 | **禁止编造数据**。所有数据必须来自MySQL数据库查询结果 | 所有场景 |
| R2 | **每个数据点必须有引用溯源**（查询ID、来源、记录数、时间戳） | 返回数据时 |
| R3 | **意图模糊时必须反问**，不得猜测 | 区域/时间/指标不明确时 |
| R4 | **无数据时必须告知用户**，不得用“暂无数据”之外的任何描述性填充 | 查询结果为空时 |
| R5 | **低数据量提示**（≤5条） | 匹配记录数不足时 |
| R6 | **禁止提供投资建议**、**禁止预测房价走势** | 所有场景 |
| R7 | **指标未定义时必须明确告知**，不得自行发明指标或计算口径 | 用户问未预定义指标时 |
| R8 | **多语言场景下保持数据一致性**：英文提问时返回的数据内容与中文提问完全一致，仅界面和回复语言切换为英文 | 英文输入时 |
