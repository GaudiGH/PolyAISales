## 一、项目概述

### 1.1 项目背景

香港房地产投资与销售领域缺乏系统化的AI深度应用，数据分散于多个平台、格式各异，整理高度依赖人工收集与Excel加工，数据获取滞后，决策支持不足。AI Agent与RAG技术已在国内市场逐步成熟，香港市场仍存在明显空白。本项目旨在通过AI技术建立一套可持续扩展的智能数据分析底座，协助团队更快掌握一二手楼盘动态，将分散的市场信息转化为可行的销售洞察。

### 1.2 项目定位

- **混合型项目**：内部投资分析团队先行使用，架构设计同时具备对外服务扩展能力
- **核心交付**：自然语言问数 + 自动化报告生成
- **数据聚焦**：首期覆盖一手住宅市场，架构预留二手数据扩展能力
- **交互渠道**：Web端为主（完整功能），微信服务号为辅（轻量问数）
- **多语言**：框架层支持中英文双语，首期以中文为主

### 1.3 项目目标（优先级排序）

| 优先级 | 维度 | 目标描述 |
| :---: | :--- | :--- |
| 1 | 用户满意度 | 简洁、快速、可信的对话式数据查询体验 |
| 2 | 数据准确度 | 每个数据点可溯源、可复核，禁止AI捏造 |
| 3 | 数据覆盖度 | 首期覆盖一手住宅物业销售资讯网全量数据 |
| 4 | 系统稳定性 | 稳定运行，可用率≥99.5% |
| 5 | 商业变现 | 首期不涉及，为后续商业化预留架构空间 |

### 4.3 数据治理模型（V1.3 更新）

**核心原则：人工修改直接覆盖，仅标记来源，不使用权重体系**

| 数据状态 | 说明 | 标记方式 |
| :--- | :--- | :--- |
| 爬虫原始采集 | 首次入库的数据，未经人工处理 | `is_manual_modified = 0` |
| 人工修改 | 管理员在后台直接修改后覆盖原值 | `is_manual_modified = 1`，记录 `modified_by_user_id` 和 `modified_at` |

**查询取数逻辑（简化）**：
- 直接查询最新数据，不考虑权重层级
- 查询结果中可筛选/展示“已人工确认”的数据（`is_manual_modified = 1`）
- 所有数据平等参与指标计算，人工修改仅作为数据来源标记

**人工精修定位**：
- 管理员在后台完成数据修正，**直接覆盖**原数据库记录
- 修改操作记录修改人和修改时间，便于追溯
- 审计日志作为可选功能，记录修改前后值

### 4.4 数据回溯与修正

| 功能 | 说明 |
| :--- | :--- |
| 数据修改 | 管理员可修改价格、面积、区域、地址、户型类型等任意字段，修改后 `is_manual_modified = 1` |
| 记录合并 | 合并重复记录，保留最优字段组合，被合并记录标记 `merged_into_id` |
| 记录存档 | 标记 `is_archived = 1`，查询时默认过滤 |
| 审计日志 | 可选记录（功能存在，不强制填写修改理由） |

### 4.5 数据模型层级（V1.3 新增）

系统采用**四层数据模型**：

```
楼盘（ai_sales_projects）
  ├── 户型分类（ai_sales_unit_types）  ← 人工精修核心
  │     └── 物理单元（ai_sales_units）
  │           └── 销售记录（ai_sales_transactions）
  └── 销售安排/说明书（ai_sales_salesbrochures）
        └── 物理单元归属
```

**各层级说明**：

| 层级 | 表名 | 说明 |
| :---: | :--- | :--- |
| L1 | `ai_sales_projects` | 楼盘主数据，包含总可售单元数（用于去化率计算） |
| L2 | `ai_sales_unit_types` | **人工精修核心**——户型分类，包含卧室/厅/卫数量、是否开放式厨房等属性 |
| L3 | `ai_sales_units` | 物理单元（具体到座/楼层/单位号），关联户型分类和销售安排 |
| L4 | `ai_sales_transactions` | 销售/成交记录，关联到物理单元 |


## 五、核心业务指标定义（预定义指标层）

**关键原则**：以下指标在系统中**预先定义、硬编码计算逻辑**。AI仅做“问题→指标映射”，不做“指标定义”或“口径解释”。所有指标的计算基于MySQL数据库中的结构化数据，通过确定性SQL执行。

### 5.1 基础统计指标

| 指标ID | 指标名称 | 业务定义 | SQL计算逻辑 | 单位 |
| :---: | :--- | :--- | :--- | :--- |
| M001 | 成交量 | 符合条件的成交记录总数 | `COUNT(*)` | 宗 |
| M002 | 成交总金额 | 符合条件的成交价总和 | `SUM(price)` | 港元 |
| M003 | 成交总面积 | 符合条件的实用面积总和 | `SUM(saleable_area)` | 平方呎 |
| M004 | 平均成交价 | 成交总金额 ÷ 成交量 | `SUM(price) / COUNT(*)` | 港元 |
| M005 | 平均成交呎价 | 成交总金额 ÷ 成交总面积 | `SUM(price) / SUM(saleable_area)` | 港元/呎 |
| M006 | 最高成交呎价 | 符合条件的最高呎价 | `MAX(price / saleable_area)` | 港元/呎 |
| M007 | 最低成交呎价 | 符合条件的最低呎价 | `MIN(price / saleable_area)` | 港元/呎 |
| M008 | 中位数成交价 | 符合条件的成交价中位数 | `PERCENTILE_CONT(0.5) WITHIN GROUP(ORDER BY price)` | 港元 |

### 5.2 时间对比指标

| 指标ID | 指标名称 | 业务定义 | SQL计算逻辑 | 单位 |
| :---: | :--- | :--- | :--- | :--- |
| M009 | 环比变化率 | (本月值 - 上月值) ÷ 上月值 × 100% | 窗口函数 `LAG` 计算 | 百分比 |
| M010 | 同比变化率 | (本月值 - 去年同月值) ÷ 去年同月值 × 100% | 窗口函数 `LAG` 指定偏移12个月 | 百分比 |
| M011 | 日均成交量 | 月成交量 ÷ 当月天数 | `COUNT(*) / DAY(LAST_DAY(date))` | 宗/天 |

### 5.3 衍生指标（需多表/多层计算）

| 指标ID | 指标名称 | 业务定义 | 计算逻辑 | 单位 |
| :---: | :--- | :--- | :--- | :--- |
| M012 | **去化率** | 某楼盘已售物理单元数 ÷ 总可售单元数 × 100% | `已售物理单元数 / total_units * 100` | 百分比 |
| M013 | **区域热度（成交量占比）** | 某区域成交量占全港成交量的比重 | `某区域成交量 / 全港总成交量 * 100` | 百分比 |
| M014 | **区域热度（价格涨幅）** | 某区域本月均价环比上月均价的涨幅 | `(本月均价 - 上月均价) / 上月均价 * 100` | 百分比 |
| M015 | **户型热度排名** | 按成交记录数统计各户型分类的排名 | `GROUP BY unit_type_id ORDER BY COUNT(*) DESC` | 排名 |
| M016 | **楼盘成交集中度** | 某楼盘成交量占所在区域成交量的比重 | `某楼盘成交量 / 所在区域成交量 * 100` | 百分比 |

### 5.4 去化率（M012）的特殊说明

去化率是房地产行业的**核心指标**，其计算基于物理单元表：

| 数据项 | 来源 | 说明 |
| :--- | :--- | :--- |
| 已售单元数 | `ai_sales_units.is_sold = 1` | 系统根据交易记录自动更新 `is_sold` 状态 |
| 总可售单元数 | `ai_sales_projects.total_units` | 从楼盘详情页爬取的“总单位数”字段 |

**系统实现要求**：
- 爬虫需采集每个楼盘的“总可售单元数”字段，写入 `ai_sales_projects.total_units`
- 若某楼盘 `total_units` 为 `NULL`，去化率指标对该楼盘**不予计算**（不猜测、不填充）
- 报告中涉及去化率时，需注明：“去化率基于已采集到总可售数据的X个楼盘计算”
- 去化率计算示例：
```sql
SELECT 
    p.id,
    p.name_zh,
    p.total_units,
    COUNT(u.id) AS total_captured_units,
    SUM(u.is_sold) AS sold_units,
    ROUND(SUM(u.is_sold) / NULLIF(p.total_units, 0) * 100, 2) AS sell_through_rate
FROM ai_sales_projects p
LEFT JOIN ai_sales_units u ON p.id = u.project_id AND u.is_archived = 0
WHERE p.total_units IS NOT NULL
GROUP BY p.id;
```

### 5.5 指标映射规则（AI理解→指标绑定）

当用户提问中包含以下关键词时，系统自动映射至对应指标：

| 用户关键词（示例） | 映射指标 | 备注 |
| :--- | :--- | :--- |
| “均价”“平均价格”“多少钱一呎” | M005 平均成交呎价 | 默认指实用面积呎价 |
| “成交量”“卖了多少套”“成交宗数” | M001 成交量 | — |
| “卖得最好”“最火”“第一名” | M015 户型热度排名 或 M013 区域热度 | 根据上下文判断维度 |
| “去化”“去化率”“卖掉多少比例” | M012 去化率 | 仅对有总可售数据的楼盘有效 |
| “涨了还是跌了”“环比” | M009 环比变化率 | 默认指均价环比 |
| “同比” | M010 同比变化率 | 默认指均价同比 |
| “总金额”“成交额” | M002 成交总金额 | — |

### 5.6 指标扩展机制

当用户提出**未预定义**的指标需求时，系统行为：
1. 识别为“未支持指标”
2. 主动反问：“系统暂未支持【XX】指标分析。您可以查询以下已支持的指标：[列出M001-M016列表]”
3. **严禁**AI自行定义或计算新指标口径

### 6.2 智能问数功能

**FR-01：自然语言查询**
- 用户通过Web或微信输入自然语言问题
- 系统执行意图识别：区域、时间、面积段、价格段、指标类型（均价/成交量/去化率/热度/排名/趋势）
- 系统执行指标映射：将意图绑定至预定义指标（M001-M016）
- 返回结构化数据结果
- 底层数据查询基于四层模型（楼盘→户型→物理单元→交易记录）

**FR-02：返回结果格式**
- 主要数据点 + 简短解读
- 每个数据点附带引用溯源标注 `[n]`
- 溯源信息包含：**查询ID、数据来源、记录数、查询时间戳**

**FR-03：引用溯源展示**
- **Web端**：引用标记可点击，弹窗显示完整溯源详情（含查询ID、来源、记录数、时间戳）
- **微信端**：以文本脚注形式呈现 `[n]`（如“[1] 一手住宅物业销售资讯网 | 87条记录”）

**FR-04：主动澄清**
以下情况系统**必须反问**而非猜测：
- 区域名称模糊（如“港岛那边”）
- 时间范围不明（如“最近”）
- 指标名称不明确（如“卖得怎么样” → 反问“您是指成交量还是均价？”）
- 用户提到未预定义的指标
- 查询条件无匹配记录

**FR-05：低数据量提示**
- 当匹配记录 ≤ 5条时，返回结果并提示：“仅找到X条记录，结果仅供参考”

**FR-06：Web端图表渲染**
- 趋势查询返回趋势图（折线图）
- 排名查询返回排名图（柱状图/横向柱状图）
- 对比查询返回对比图（分组柱状图）

### 6.3 报告生成功能

**FR-08：报告交付**

## 八、后台管理功能（V1.3 重构）

### 8.1 核心管理模块

后台管理以**户型类型管理**为核心，辅以物理单元管理和销售记录管理。

#### 8.1.1 户型类型管理（核心精修模块）

**功能定位**：这是后台管理的**核心功能**，所有数据精修工作围绕户型类型展开。

| 功能 | 说明 |
| :--- | :--- |
| **列表浏览** | 按项目/销售安排筛选，展示所有户型类型记录，高亮 `is_manual_modified=1` 的记录 |
| **新增户型** | 为某楼盘创建新的户型类型，填写 `unit_name`、卧室/厅/卫数量、是否开放式厨房、阳台数量、露台面积、是否复式等 |
| **编辑户型** | 修改户型名称或属性，修改后自动设置 `is_manual_modified=1`、记录修改人和时间 |
| **关联售楼说明书** | 编辑页面可查看该楼盘关联的 `ai_sales_salesbrochures` 列表，管理员可**打开PDF对照**户型信息，辅助判断 |
| **批量绑定** | 将一批物理单元批量绑定到某个户型类型（如“A座2-27楼A室”全部绑定到“2房2厅”） |
| **删除/归档** | 归档不再使用的户型类型 |

**户型精修操作流程**：

```
1. 管理员进入户型类型管理 → 按楼盘筛选
2. 查看该楼盘关联的销售安排列表 → 点击PDF链接打开售楼说明书
3. 对照PDF中的单位分布/户型描述 → 判断该楼盘包含哪些户型
4. 新增/编辑户型类型 → 填写标准化名称和结构化属性
5. 进入物理单元管理 → 将对应物理单元批量绑定到该户型类型
6. 绑定后，该楼盘下的交易记录可按户型类型进行聚合统计
```

**典型精修场景**：

| 场景 | 操作 |
| :--- | :--- |
| 爬虫新增楼盘，自动生成未知户型类型 | 管理员对照售楼说明书PDF → 重命名/补全户型属性 |
| 爬虫识别户型名称不准确（如“2房2厅”与“两房两厅”） | 管理员统一修正为标准化名称 |
| 新销售安排推出，包含新户型 | 管理员新增户型类型，绑定对应物理单元 |
| 户型属性缺失（如阳台数量、是否复式） | 管理员对照PDF补全 |

## 九、AI Agent行为规则（核心约束）

以下规则为硬约束，任何Agent不得违反：

| 规则编号 | 规则内容 | 触发场景 |
| :---: | :--- | :--- |
| R1 | **禁止编造数据**。所有数据必须来自MySQL数据库查询结果 | 所有场景 |
| R2 | **每个数据点必须有引用溯源**（查询ID、来源、记录数、时间戳） | 返回数据时 |
| R3 | **意图模糊时必须反问**，不得猜测 | 区域/时间/指标不明确时 |
| R4 | **无数据时必须告知用户**，不得用“暂无数据”之外的任何描述性填充 | 查询结果为空时 |
| R5 | **低数据量提示**（≤5条） | 匹配记录数不足时 |
| R6 | **禁止提供投资建议**、**禁止预测房价走势** | 所有场景 |
| R7 | **指标未定义时必须明确告知**，不得自行发明指标或计算口径 | 用户问未预定义指标时 |
| R8 | **多语言场景下保持数据一致性**：英文提问时返回的数据内容与中文提问完全一致，仅界面和回复语言切换为英文 | 英文输入时 |
